# Riftbound collection system: final design (ADR-002, revision 2)

Status: accepted for implementation. Repos: scanner package + CLI + iOS app at `/Users/luke/Documents/GitHub/RiftboundScanner` (committed at 1c8944f; package `Sources/RiftboundRecognizer`, CLI `Sources/riftscan`, app `App/`), collection server at `/Users/luke/Documents/GitHub/RiftboundCollection` (3 commits, Docker on the Pi `tronbyt`, `http://riftbound.local` and `http://riftbound.lan`, port 8096). This revision applies the review of revision 1; it is self-contained and supersedes it. Section 13 lists the refutations that were rejected and why.

## 1. Context

Luke owns about 1,700 Riftbound cards in five sealed boxes and wants one source of truth for the collection on his home server, a feeder-driven scanning flow that records those cards without a tap per card, decks built from cards he owns, and a recogniser that gets better as he confirms scans. Three pieces exist and do not talk to each other:

- The iOS app drives a TCG Archivist CSC100 feeder over BLE, identifies each card with the `RiftboundRecognizer` package (Vision feature print + three perceptual hashes per printing, one descriptor per printing in the bundled `index.json`, OCR of the printed code) and stores `ScanRecord`s in `Documents/Scans/<batch>/{batch.json, scans.json, photos/, rectified/}` through one protocol, `ScanStoring`, whose only live implementation is `FileScanStore`. The Collection tab derives ownership by folding every confirmed scan (+1 each), so re-scanning doubles holdings; nothing leaves the phone except a USB pull. `acceptConfidentScans` (1c8944f) writes `.correct` verdicts with no provenance.
- The server is FastAPI + SQLite: `cards` keyed by vault code (`OGN-001`, `VEN-038A`, `SFD-227-STAR`, `OGN-066-P`), append-only `ledger` with a `holdings` view, idempotent all-or-nothing `POST /api/ledger/batches`, decks with five slots, daily tcgcsv prices, a server-rendered web UI, `import_catalog` run unconditionally inside the FastAPI lifespan on every boot. No migrations, no scan tables, no client timestamps on events; a batch fails entirely on one unknown card id; the deployed ledger is empty (0 events on 2026-11-07).
- The recogniser has no learned state. Measured on 113 labelled scans: real-photo exemplars lift same-card feature-print cosine from a median 0.748 (render) to 0.915; two confident scans (exact code, fused >= 1.0) were wrong because OCR read `024` for `014`, and in both an exemplar of the true card scored 0.911 against the photo versus 0.591 for the OCR-named render. Hashes do not transfer between captures (dHash 0.578 vs 0.812). Tray-locked canvases in the pre-crop batches would poison a naive exemplar store. 37 % of judged scans matched upside down. `GenerateImageFeaturePrintRequest.Revision` has exactly one case (`revision2`) in the iOS 27.2 and macOS SDKs, so the enum cannot detect embedding drift.

Hard constraints: Swift 6.2 defaults in the app (MainActor default isolation, approachable concurrency, structured concurrency, no `Task.detached`), value types, initializer injection from one composition root, state-complete UX with Dynamic Type and VoiceOver, Swift Testing; the Pi has ~906 MB RAM (swap in use, memory cgroups not enabled in `cmdline.txt`) and no Vision, so descriptors are computed on the phone or Mac only; Riot card images and URLs are never stored on the server or committed; the app is a personal build; existing `scans.json` and `Scripts/summarize-scans.py` keep working; everything ships incrementally with tests at each step.

Measured facts this design rests on (re-verified against the files on 2026-11-07): normalising recogniser keys with `*` -> `-STAR`, trailing `a` -> `{a,A}` and the total stripped resolves 1,403 of 1,408 index printings to a vault code; the 5 misses are tokens UNL-T01/T06/T07/T08 and VEN-T04 (vault spells back faces `UNL-T01g`). The naive "strip the denominator" key rule collides on four oversized promos (`OGN-279/298` vs `OGN-279`, likewise 288, 294, 296). Index ids with `*` are `ogn-NNN*-298`, `sfd-NNN*-221`, `unl-NNN*-219`, `ven-NNN*-166` (one total per set). 345 of 1,822 vault names carry a trailing parenthetical and some carry a third ` - ` segment (`Annie - Dark Child - Starter`). Finish availability: 1,037 foil-only, 597 both, 181 normal-only, 7 neither; 34 vault flags disagree with tcgcsv. The "Testing" batch holds 85 judged scans over 47 distinct printings from a ~34-card stack fed repeatedly, mixing four photo formats; `crop` is present on 33 records only. BF7582A9 has `wholeImage` placement on 7 of 14 scans. The two confident-but-wrong scans have descriptor scores 0.642 and 0.575; correct confident scans in the clean batch sit at 0.578-0.611, so no descriptor floor near 0.60 separates them. In 10 of 64 correct code-read scans another saved candidate beats the top by > 0.02 on descriptor score.

## 2. Principles that break ties

1. The server's SQLite ledger is the only source of truth for holdings. The phone shows server holdings plus its own unacknowledged deltas when offline; it never computes ownership from scans again.
2. Every write leaving the phone carries a deterministic client reference and is applied per item; an undo names the applied row it reverses rather than recomputing it. A feeder jam, an unknown key or a flaky VPN leaves a consistent partial state and every terminal outcome is visible.
3. Humans label; machines propose. Auto-accepted scans enter the ledger (the point of a feeder) but are tagged, never feed exemplars, and are audited at a policy-set random rate so precision is bounded, not assumed.
4. The Pi does JSON, SQL and C-implemented dot products only, off the request path. Every artefact it serves is versioned data; every threshold is a policy value.
5. Additive schema changes everywhere: optional keys on `ScanRecord` with safe legacy defaults, `PRAGMA user_version` migrations applied explicitly, format-versioned overlay and policy files.
6. Nothing irreplaceable lives in one place: nightly ledger backups pulled to the Mac; a phone photo is pruned only after the server holds the photo or a downsampled copy, and never for calibration batches.
7. Durable truth on the phone is `scans.json` (decisions) plus `sync.json` (acknowledgements); the outbox is a cache that can be deleted and rebuilt.
8. Labels are snapshots: a decision records the card id it confirmed; nothing that re-ranks candidates later can change a label.

```swift
  case terminal(SyncStatus) }                                        // duplicate, duplicateMismatch, unknownCard(catalogVersion), wouldGoNegative, nothingToUndo, invalid
enum UploadState: Hashable { case notEligible, queued, uploaded(Date), conflict(serverSeq: Int), failed(String) }
struct ScanSyncState { var items: [String: LedgerItemState]; var record: UploadState; var photoSmall, canvas, photo: UploadState }
protocol ScanStoring { ...; func decide(_ id: ScanRecord.ID, _ input: DecisionInput) async throws -> ScanRecord }
```
`SyncingScanStore.update(_:)` throws `staleRecord` when the incoming `decisions` is not a strict extension of what is on disk. `acceptConfidentScans` calls `store.decide` per record after re-reading the batch.

## 5. Sync protocol

Snake_case on the wire; `X-Client` header; weak ETag comparison server-side.

### 5.1 Ledger items
`POST /api/sync/ledger`, up to 100 items, processed in order inside one `BEGIN IMMEDIATE` with `SAVEPOINT`/`RELEASE`/`ROLLBACK TO` per item:
```json
{"device":"iPhone17,1","items":[
 {"client_ref":"scan:8D59…:2:undo","undo_of":"scan:8D59…:1","occurred_at":"…","scan_id":"8D59…"},
 {"client_ref":"scan:8D59…:2","card_key":"VEN-014","finish":null,"default_finish":"normal","quantity_delta":1,"occurred_at":"…","scan_id":"8D59…"},
 {"client_ref":"manual:3F2A…","card_key":"OGN-066-P","finish":"foil","quantity_delta":2,"condition":"NM"}]}
```
Response 200 with `results[]` `{client_ref, status, card_id, finish, ledger_id, finish_warning?}`, `status` in `applied | duplicate | duplicate_mismatch | unknown_card | would_go_negative | nothing_to_undo | invalid`. An undo item copies card and finish from the row whose `client_ref == undo_of` and inserts its negation; no such row -> `nothing_to_undo`. A replayed `client_ref` whose `item_hash` differs -> `duplicate_mismatch` (surfaced as needs-attention). `would_go_negative` writes nothing and is terminal. The legacy `POST /api/ledger/batches` stays for scripts with `payload_hash` and 409 on a differing replay.

### 5.2 Scan records and assets
- `PUT /api/scans/batches/{id}` upsert.
- `PUT /api/scans/{id}` body `{record, descriptor{calibration_hash, orientation, feature_print, hashes}, reference_similarity, best_other_reference, code_alternatives[], analysis_stamp, engine}`. Decisions follow seq rules (201/200/`unchanged`/409 `seq_conflict`, appended idempotently to `scan_verdicts`); analysis columns, descriptor and similarities are updated whenever `analysis_stamp` differs from the stored hash even at equal seq, returning `{"updated":["analysis"]}` and re-running admission. Unknown batch -> 200 `{deferred:true}`. Changed confirmed card -> exemplar revoked (`verdict_changed`) and re-admission for every scan whose last `admission_log` row names it as blocking.
- `PUT /api/scans/{id}/photo_small` (<= 400 KB), `/canvas` (<= 400 KB), `/photo` (<= 3 MB), `X-Content-SHA256`, JPEG magic check; 201/200/404/409/413/507.
- `GET /api/scans…` list/detail/assets.

### 5.3 Learning artefacts
`GET /api/learning/overlay/meta?calibration=<hash>`, `GET /api/learning/overlay?calibration=` (full, ETag), `GET /api/learning/overlay/changes?since_version=&calibration=` (body `{baseVersion, version, calibrationPrint?, added: [exemplar], revoked: [scan UUID]}`, decoded by `ExemplarDelta`; `revoked` lists the **scan ids** of the revoked exemplars, never the server's integer exemplar ids, because the wire exemplar carries no server id and the gate admits at most one exemplar per scan; 410 when the base version is gone, client falls back to full), `GET/PUT /api/learning/policy`, `POST /api/learning/admit`, `POST /api/learning/admit/dry-run` (gate inputs -> decision, for `riftscan gate-diff`), `POST /api/learning/overlay/build`, `POST /api/learning/exemplars/{id}/revoke`, `POST /api/learning/conflicts/{id}/resolve`, `GET /api/learning/stats` (Wilson bound, audits by source, exemplars by set, sittings, versions), `POST/GET /api/learning/evaluations` (refused with 422 when `excluded_batch` is empty while any case's scan is an exemplar source), `GET /api/learning/ocr-readings`.

### 5.4 Reads the app depends on
`GET /health` (`user_version, api_version 2, catalog_version, last_backup_at, free_disk_mb, rss_mb, assets_bytes, scans_stored, exemplars, overlay_versions, catalog_warnings`), `GET /api/holdings` (ETag by ledger head), `GET /api/ledger?since_id=`, `GET /api/catalog`, `GET /api/prices/latest`, `GET /api/cards/resolve?keys=`, decks routes, `GET /api/formats`.

### 5.5 Conflict model
Append-only ledger; both writers append. Undo is by reference, so the only cross-writer conflict is an undo after a web `-1` emptied the holding: `would_go_negative`, terminal, shown with "Resolve on the web". Records are last-writer-by-seq with 409 terminal on the phone (`UploadState.conflict`). Voiding completes when every item is terminal; the overview shows the count of rejected undos. Decks are server-authoritative, online-only.

## 7. Learning loop

Admission gate (`ExemplarAdmission`, `gate_version` 2; Swift struct, Python port, shared `admission-cases.json`). Similarity contract: Float64 accumulation over Float32 inputs, rounded to 4 decimals before any comparison; the fixture includes vectors at each threshold ± 0.00005. A scan is admitted for its `ArtGroup` when: (1) latest decision source is `human`, `audit` or `spotCheck`, kind `correct`/`corrected`, `cardID` present; (2) placement `detected`; (3) `calibrationHash` equals the overlay's; (4) `captureQuality == standard` and the batch override is not `legacy`; (5) tier `code`: `codeSource == edgeBand`, winning code `literal`, exact agreement with the confirmed card, `referenceSimilarity >= 0.62` (sanity floor), and the confirmed card's reference similarity exceeds every `codeAlternatives` entry naming a different `ArtGroup` by >= 0.05 (the 014/024 case has 0.16 of margin); tier `artCorroborated`: no code read, two distinct human `corrected`/`correct` scans of the same `ArtGroup` from different capture ids with mutual fp >= 0.85 and both `referenceSimilarity >= 0.60` admit together; a single witness logs `needsSecondWitness`; (6) exemplar-impostor: an existing exemplar of a different `ArtGroup` with fp >= 0.90 to the query records `admission_log.blocking_exemplar_id` and an `exemplar_conflicts` row; two distinct human scans colliding with the same exemplar auto-revoke it (`conflict`) and re-run admission for the blocked scans; `/learning` shows both canvases with "Which is right?"; (7) dedupe at fp >= 0.985; (8) cap 6 per group: the medoid (highest mean similarity to the group's admitted scans) first, then farthest-point among candidates whose `referenceSimilarity` is in the top half. The reference-impostor margin rule of revision 1 is dropped. Thresholds live in `LearningPolicy.admission`.

Overlay: built per calibration hash nightly after backups, on `POST /overlay/build`, or at most once per hour when admissions changed; `overlay_changes` feeds the delta endpoint. Wire format JSON (`formatVersion 2, version, calibrationPrint, exemplars[{artGroup, featurePrint, scanID, batchID, admittedAt}]`); on the phone it is stored as a binary file (header + packed Float32 + id table) patched by deltas. A delta's `revoked` entries are scan UUIDs (`Exemplar.scanID`); the server resolves its `overlay_changes.exemplar_id` rows to the exemplars' `scan_id` before serving them. Sizing: with the 0.985 dedupe and the 6-per-group cap, one box yields on the order of 300–700 exemplars (~1–2 MB JSON, ~1 MB binary), not thousands; the full-cap bound is ~8,400 exemplars (~26 MB JSON), which is why deltas and the binary store exist.

Matching: `DescriptorMatcher(policy:exemplars:excluding:)` gives every group member the same `exemplarFP`; `excluding: Set<ScanBatch.ID>` drops exemplars by `batchID` (used by on-device re-identify). With an empty overlay results are bit-identical to today. The per-hypothesis shortlist stays bounded by `rerankedCandidateCount` (12): the best `limit` by fused score, with the best reference match always kept (it displaces the weakest fused candidate), so the hypothesis's reference standing never depends on the overlay; a confidently read code may still inject one more entry per matching printing, so `ScanAnalysis.shortlist` truncates `matches` to 12.

Phone hot-reload: `LearningSync` checks meta with stored versions on launch, foreground and after a successful flush; downloads full or delta, verifies `calibrationPrint` compatibility, swaps atomically and calls `install`, which parks during a lease. `LearningState`: `idle / checking / upToDate / updated / updatePending / incompatible(reason: embeddingChanged|dimension) / failed`.

Evaluation protocol: `riftscan import-scans` (one case per human/audit/spot-check decision; `samplingWeight` = 1 for reviewed, 1/auditRate for audit cases; photos loaded at 4096 px; image size recorded); `build-overlay --exclude-batch` runs the Swift gate and prints the exemplar count per fold; a fold with zero exemplars **fails**, it does not pass; `evaluate` reports raw and weighted top-1, confident precision/coverage, exemplar-hit rate; `admission-report` prints impostor p50/p95/p99, the 0.62 floor's ROC and admit/reject reasons; `gate-diff` posts the same inputs to `/admit/dry-run` and reports mismatches. On-device: `ReidentifyModel` builds its recogniser with `overlay.excluding(batch:)`, writes `excluded_batch` and `exemplar_count_used` into the run; the server refuses runs that evaluate on training data. The three old batches seed exemplars (whatever the gate yields on phone-recomputed analyses; the count is measured, not assumed) and are a smoke set only; box 1's first ~100 human-reviewed scans become the first real held-out set. Shipping rule: an overlay or policy ships only when every held-out fold with a non-zero exemplar count is not lower than baseline on top-1 and confident precision, confirmed by an on-device excluded-batch run.

Phase 2 (>= 300 human labels, >= 3 sittings): `riftscan calibrate` fits a logistic P(correct) with sampling weights and leave-one-batch-out; `riftscan ocr-confusions` derives repair pairs.

## 12. Open risks
- Calibration-print compatibility threshold is unmeasured until `check-revision` runs on both platforms; if iOS and Mac prints diverge, the Mac-built index and phone exemplars live in different spaces and the Mac evaluation becomes indicative only.
- Gate thresholds (0.62, 0.05 alternative margin, 0.85/0.60 two-witness, 0.90 impostor, 0.985 dedupe) rest on tens of pairs; `admission-report` runs before the first overlay ships; the overlay can be emptied server-side.
- Auto-accepted scans enter the ledger at a measured ~3 % error rate today; with a 30 % audit rate box 1 can bound precision to roughly 97–98 %, and that is the honest claim.
- Same-art twins remain OCR-only by design.
- Per-item sync and terminal statuses mean partial success is normal; the needs-attention rows must stay prominent.
- Foreground-only sync.
- Token off by default; any LAN device can write until it is set.
- The gate exists twice; the shared fixture, the similarity contract and `gate-diff` keep them aligned.
- The vault generator must reproduce the 1,822 codes; until then catalog refresh is manual.
- The Pi memory cap depends on a reboot Luke must schedule.
- The three legacy batches may seed very few exemplars after per-record quality and placement rules; coverage comes from box 1.

## 13. Rejected refutations
- **"Ship `catalog/index-ids.txt` as runtime data for recogniser aliases and the same-art-sibling flag."** Rejected. Resolution by normalisation needs no id list, and under `ArtGroup` keying the sibling refusal disappears (an exemplar helps all members equally and OCR decides), so the Pi never needs to know what is in the index. The list stays a test fixture.
- **"The overlay is 9 MB after one box (~3,000 exemplars)."** The number is wrong: dedupe and the 6-per-group cap bound one box to hundreds of exemplars (~1–2 MB). The churn problem (rebuild per minute during review) is real and is fixed; the size claim is corrected rather than designed around.
- **"Tier art is refused for same-art siblings" (revision 1 rule 5) and the refutation asking for a hand-maintained flag.** Both superseded: keying by `ArtGroup` makes the question moot.
- **Reference-impostor margin fix "keep the exemplar-impostor clause across ArtGroups" vs the conflict-handling refutation.** Both accepted together; no conflict.
