**A4 deviations from ADR-002 (with reasons; guide §13):**

- `LedgerItemState` gains `sent` (§4.2 amendment): an item handed to the server whose answer never arrived. The 3 s probe over the VPN makes a timeout after the server's commit a normal event; without the state a +1 that landed looked never sent, so a later correction withdrew it silently and the holding stayed one too high. The builder replays a `sent` +1 (the server answers `duplicate` or `applied`) and then reverses it by reference.
- `terminal(SyncStatus)` is spelled `terminal(TerminalStatus)` with an extra `unrecognized(raw)` case, so a status this build does not know is kept verbatim and shown rather than crashing the decode or being retried forever.
- `applied(... finish: Finish?)`: the server's `finish` is nullable on the wire for keys it could not resolve; the phone keeps what it was told.
- `ScanSyncState.uploadedSeq` records how many decisions the server's copy of the record had, so a longer log re-queues the record without a second write path.
- `UploadState.failed` is retried on the next flush rather than terminal: every refusal the server can give an upload (413, 422, 507) depends on server-side state that changes; 409 alone is terminal, as written.
- Records are uploaded for decided scans only (decision 4 says "always"): a pending scan has nothing the admission gate can use, and the record goes up with its first decision.
- A voided batch's folder is kept when an undo was refused (§5.5 says removed once every item is terminal): the count of refused undos must stay visible with "Resolve on the web" until the user deletes the batch.
- Voiding appends `voided` to pending scans too, so the server learns the scan existed and was discarded; a voided scan uploads its record and no asset.
- A ledger page refused as a whole with 422 is bisected to the one bad item, which ends `invalid`; other non-retryable refusals of the route (404, unreadable answer) leave the items `sent`, let records and assets drain, and end the flush `failed` with the message, so one bad page cannot hold the rest of the queue.
- Pull-to-refresh is not yet a sync trigger (History's refresh reloads the list only); it joins the triggers with the Collection tab in A9.
